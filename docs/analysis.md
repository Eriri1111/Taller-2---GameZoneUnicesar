# System Analysis & Design Document (analysis.md) This document provides rigorous technical justifications and answers to the guiding architectural questions for the **GameZone Unicesar** information system [cite: 1]. --- ## Part 1: Persons and Roles Hierarchy ### 1. Common Attributes vs. Specific Attributes and Class Hierarchies * **Answer**: All persons interacting with the store share common identification and contact data: full name, government identification number, and telephone number. However, specific roles introduce distinct attributes: **Customers** require an email address and a purchase history record, whereas **Employees** require a unique employee code and an assigned work shift schedule. In an object-oriented class hierarchy, this distinction is modeled via generalization: a base abstract class (`Person`) holds the shared attributes, while specialized subclasses (`Customer`, `Employee`) inherit these attributes and extend them with role-specific fields. ### 2. Generic Person Class Justification and Instantiation * **Answer**: A generic `Person` class should exist to encapsulate shared properties and behaviors, reducing code duplication across subclasses through inheritance. However, because a person in the business domain must always fulfill a concrete operational role (either a customer or an employee) and cannot exist as an unclassified entity within the store context, the base class must be declared as **abstract**. This prevents direct instantiation of incomplete generic entities, enforcing strict domain integrity. --- ## Part 2: Products Hierarchy and Polymorphism ### 3. Common Product Characteristics vs. Specific Attributes * **Answer**: Regardless of category, all products share inventory and catalog metrics: a unique product identifier, title, unit price, and available stock quantity. Specialized products introduce unique fields: **Video games** include platform type, genre, and age classification ratings, while **Consoles** feature hardware brand, model specification, and generation tags. ### 4. Comprehensive Description Behavior and Polymorphism * **Answer**: To allow every product type to format its own specialized description combining general and specific attributes, an abstract method (e.g., `public abstract String getDescription();`) is declared in the base `Product` class. This forces all concrete subclasses (`VideoGame`, `Console`) to provide their own implementation using the **polymorphism** mechanism of object-oriented programming, ensuring dynamic method dispatch at runtime. --- ## Part 3: Sales and Entity Relationships ### 5. Nature of Relationships Involving Sales * **Answer**: A sale transaction links a `Customer` (aggregation), an `Employee` (aggregation), and a collection of one or more `Product` items (composition/association). These relationships are associative and aggregative; the sale references participants without tightly binding their entire lifecycle, except for stock items whose quantities are directly controlled by transaction workflows. ### 6. Responsibility for Calculating the Sale Total * **Answer**: The calculation responsibility belongs inside the `Sale` class itself. Because the sale maintains the internal collection of purchased products and their quantities, it possesses all necessary data to compute the aggregate financial sum, adhering to the principle of information hiding and encapsulation. --- ## Part 4: Business Rules and Validations ### 7. Enforcing Minimum Product Constraint in Sales * **Answer**: To guarantee that a sale cannot be registered without at least one product, validation logic must be enforced inside the transactional service layer (`SaleService`) and protected by the `Sale` constructor or item-addition methods, throwing an exception if the product list is empty. ### 8. Automated Inventory Stock Update Mechanism * **Answer**: When a sale is confirmed, the system must iterate through the purchased items and deduct quantities from available inventory. This operation involves collaboration between the `SaleService` (which orchestrates the transaction), the `ProductService` (which verifies stock availability), and the `Product` domain models (which update their stock counts). --- ## Part 5: Layered Architecture Organization ### 9. Layer Classification and Criteria * **Answer**: The system is organized into four distinct layers: * **Model**: Contains domain entities and business objects (`Product`, `Person`, `Sale`). * **Persistence**: Contains file-handling data access components (`ProductRepository`, `PersonRepository`, `SaleRepository`). * **Service**: Contains business rules, validations, and workflow controllers (`ProductService`, `PersonService`, `SaleService`). * **UI**: Contains interaction menus (`ConsoleUI`, `Main`). * *Criterion*: Classes are categorized based on their primary responsibility: data structure representation goes to model, file serialization to persistence, business rules to services, and user input/output handling to UI. ### 10. Separation of File I/O Logic from Domain Classes * **Answer**: Domain classes should remain pure representations of business concepts. Mixing file persistence code inside domain entities introduces tight coupling, violates the Single Responsibility Principle, makes unit testing difficult, and tightly couples data storage formats directly to business objects. ### 11. Layer Dependency Rules and Justifications * **Answer**: Permitted dependencies flow unidirectionally downward: UI depends on Services; Services depend on Model and Persistence; Persistence depends on Model; Model depends on no other layer. This strict hierarchy isolates user interaction and storage mechanisms from core business logic, maximizing modularity and maintainability.
